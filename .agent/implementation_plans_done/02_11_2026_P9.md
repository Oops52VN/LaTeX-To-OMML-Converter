## 1. Goal Description
Diagnose and resolve the issue preventing `run.bat` from launching the application, ensuring seamless, silent startup across different Windows Python installations (WindowsApps, direct MSI installers, virtual environments) without missing module or interpreter mismatch errors.

---

## 2. Root Cause Analysis
1. **Python Interpreter Path Ambiguity in PATH**:
   - The user's system had multiple Python installations:
     - `C:\Users\trann\AppData\Local\Microsoft\WindowsApps\python.exe` (Python 3.13 with all required packages installed).
     - `C:\Users\trann\AppData\Local\Python\bin\python.exe` / `pythonw.exe` (Python 3.14 without dependencies).
   - Calling plain `pythonw` in `run.bat` invoked the Python 3.14 `pythonw.exe` located earlier in PATH, which immediately crashed due to missing `numpy` and other dependencies.
2. **Execution from Root Directory & Module Import Resolution**:
   - Running `python app\app.py` from the project root sets `sys.path[0]` to the project root instead of `app/`, which could cause sibling imports (such as `latex_omml_engine`, `image_omml_engine`, and `edge_pdf_viewer`) to fail if not explicitly present in `sys.path`.

---

## 3. Scope & Technical Architecture
1. **Self-Resolving `run.bat` Engine**:
   - Pre-flight check: Validates that `python` is accessible in the environment.
   - Dynamic binary resolution: Queries the exact active Python interpreter (`sys.executable`) via a fast inline command to locate its matching `pythonw` / `pythonw3` / `pythonw3.13` binary.
   - Fallback hierarchy: Tries resolved binary -> `pythonw3` -> `pythonw` -> `python`.
   - Silent execution: Retains background execution (`start ""`) without an intrusive terminal window.
2. **`app/app.py` Self-Configuring `sys.path`**:
   - Added explicit initialization at the very top of [`app/app.py`](app/app.py) ensuring both the script directory (`app/`) and project root are guaranteed to exist at `sys.path[0]` and `sys.path[1]`.
